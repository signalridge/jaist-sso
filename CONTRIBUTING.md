# Contributing and releasing

Use Bun 1.4.4 or later and install the committed lockfile:

```sh
bun install --frozen-lockfile
bun run check
bun run pack:check
```

Biome, TypeScript, Bun types and Changesets are development dependencies only.
Consumers do not install them. The library and CLI run TypeScript directly on Bun.
CI checks Linux and macOS without real credentials. Keep tests synthetic; never
commit certificates, passwords, cookies, SAML messages or diagnostic HTTP dumps.

## Versioning

A change to shipped `src/`, README, LICENSE, or package metadata needs a changeset:

```sh
bun run changeset
bun run changeset:status
```

Commit the entry with the change. Use an independent SemVer version for this
package; a documentation change shipped to npm needs a patch. Development tooling
alone does not need a release. Do not edit the version or create release tags by
hand in the normal workflow.

## GitHub Actions

The `publish.yml` workflow runs on `main`. Changesets creates or updates
`changeset-release/main` and its Version Packages PR, including package version,
changelog and Bun lockfile. CI is explicitly dispatched on that branch because
PR events generated by `GITHUB_TOKEN` do not reliably start other workflows. If
GitHub holds a bot-created PR run for approval, the release workflow approves only
its own same-repository release PR at its current SHA. Review the version diff and wait for Linux/macOS CI before merging the PR.

After merge, the publisher verifies the consumed changeset, increased version,
merged same-repository release PR and exact shipped contents at the reviewed PR
head. Only that snapshot can be published. Ordinary commits with no changesets
do not republish an old version. Stale ordinary main jobs skip version PR writes;
rerunning the original release job can still reconcile its authenticated snapshot.

The workflow uses the temporary repository token and npm Trusted Publishing/OIDC
with provenance. Both existing npm packages are bootstrapped. Their Trusted
Publisher settings must retain the repository, `publish.yml` filename and
`npm-publish` GitHub environment. No npm token secret or personal access token is
required. Repository Actions settings must allow GitHub Actions to create pull
requests; the job requests only contents, pull-request, Actions dispatch and OIDC
permissions.

## Recovery

Rerun the failed **original workflow run**. The publisher checks npm's exact
version integrity before publishing, waits for registry propagation and resumes
GitHub release creation if npm already accepted the identical archive. Network,
authentication and rate-limit failures never mean an npm version is absent.
An integrity mismatch requires a new version; do not overwrite or unpublish it.
Older reruns cannot move npm's `latest` tag backwards. Existing release tags must
point to the original merge commit. GitHub releases use the version's changelog
entry and attach the exact npm tarball.

A workflow dispatch on current `main` updates a pending Version Packages PR or
reconciles a release only if that revision is itself the release merge. It does
not recover a different historical revision. Use the original run for that case.
